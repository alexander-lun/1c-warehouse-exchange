# Склад: обмен с маркетплейсом

Конфигурация 1С:Предприятие 8.5 — небольшой склад, который получает заказы с маркетплейса, резервирует под них товар и отдает остатки обратно. Снаружи доступен REST API для WMS/курьерской службы.

Что внутри:

- **REST API на HTTP-сервисе** — остатки, приемка товара, заказы, смена статуса, ручной запуск обмена. Ключ API в заголовке `X-Api-Key`. Описание — [docs/openapi.yaml](docs/openapi.yaml).
- **Обмен с маркетплейсом** — загрузка заказов (инкрементально, по дате изменения), выгрузка остатков, отправка статусов. Регламентное задание + ручной запуск через API.
- **Контроль остатков при проведении** по «новой методике»: управляемая блокировка через `БлокироватьДляИзменения`, запись движений, затем проверка текущего остатка. Проверка на момент документа здесь не годится: два заказа, проведенные в одну секунду, не видят движений друг друга (покрыто тестом с параллельным проведением).
- **Журнал обмена** — регистр сведений с результатом каждой операции.
- **Интеграционные тесты** на pytest против опубликованной базы и заглушки маркетплейса.

## Как работает обмен

Маркетплейс отдает заказы, измененные начиная с указанной даты (включительно). Отметка «загружено по» хранится в константе.

- Заказ сопоставляется по идентификатору маркетплейса, поэтому повторная загрузка не создает дублей — уже загруженные заказы без изменений пропускаются.
- Если заказ не удалось провести (не хватает товара), он **сохраняется непроведенным**, а не теряется. При следующей загрузке или смене статуса заказ проводится снова — уже текущей датой: резерв возникает в момент проведения, а не в момент первой попытки.
- Если в заказе неизвестный артикул, заказ не создается. Отметка «загружено по» не сдвигается дальше первого заказа с ошибкой, чтобы он попал в следующую загрузку.
- Отмена заказа (с маркетплейса или через API) перепроводит документ без движений — резерв снимается.
- Ошибка отправки статуса на маркетплейс не откатывает смену статуса в 1С: заказ попадает в очередь (регистр `ОчередьОтправкиСтатусов`), и статус отправляется повторно регламентным заданием или `POST /exchange/push-statuses`. Если маркетплейс сам прислал новый статус заказа, запись очереди снимается.
- Параллельные загрузки не создают дублей: заказ, который успела создать соседняя загрузка, считается пропущенным.

## Метаданные

| Объект | Назначение |
|---|---|
| Справочник `Номенклатура` | товары, артикул индексирован |
| Документ `ПоступлениеТоваров` | приход на склад |
| Документ `ЗаказМаркетплейса` | заказ: идентификатор, статус, товары; расход с контролем остатков |
| Регистр накопления `ОстаткиТоваров` | остатки |
| Регистр сведений `ЖурналОбмена` | результаты операций обмена |
| Регистр сведений `ОчередьОтправкиСтатусов` | статусы, которые не удалось отправить: число попыток, последняя ошибка |
| Перечисления `СтатусыЗаказов`, `НаправленияОбмена` | |
| Константы | адрес и токен маркетплейса, ключ API, отметка загрузки |
| Общие модули `ОбменСМаркетплейсом`, `РаботаСJSON`, `НастройкиОбменаВызовСервера` | |
| HTTP-сервис `APIСклада` (`/hs/api`) | REST API |
| Регламентное задание `ЗагрузкаЗаказовМаркетплейса` | загрузка заказов и выгрузка остатков |

Исходники в `src/` — выгрузка конфигурации в файлы (формат конфигуратора).

## Запуск

Нужны платформа 8.5 (проверено на 8.5.1.1522, Linux), Apache 2.4 и Python 3.11+.

```bash
# база из исходников (+ проверка модулей)
scripts/build.sh build/ib

# ключ API и адрес маркетплейса
scripts/configure.sh build/ib http://127.0.0.1:8090 dev-token my-api-key

# публикация на локальном Apache от текущего пользователя
scripts/publish.sh build/ib warehouse 8081

curl -H 'X-Api-Key: my-api-key' http://127.0.0.1:8081/warehouse/hs/api/stock
```

Для публикации на «обычном» Apache достаточно описать точку публикации в `default.vrd` с `<httpServices publishByDefault="true"/>` и подключить к ней обработчик `1c-application` модуля `wsap24.so` — пример в [scripts/publish.sh](scripts/publish.sh).

Настройки можно задать и вручную: раздел «Склад» → константы.

## Тесты

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
API_KEY=my-api-key PYTHON=.venv/bin/python scripts/test.sh -v
```

`scripts/test.sh` поднимает заглушку маркетплейса ([mock/marketplace.py](mock/marketplace.py)) на порту 8090 и запускает тесты из `tests/`. База между запусками не очищается — тесты используют уникальные артикулы и номера заказов.

CI (GitHub Actions) на каждый push: анализ кода 1С BSL Language Server (сборка падает при любом замечании), ruff для Python. Интеграционные тесты требуют платформу и запускаются локально.

Статический анализ — [BSL Language Server](https://github.com/1c-syntax/bsl-language-server), настройки в `.bsl-language-server.json`:

```bash
java -jar bsl-language-server.jar --analyze --srcDir src --configuration .bsl-language-server.json --reporter console
```

## Ограничения

- Пользователи и роли не настроены — база работает без авторизации пользователей, API закрыт только ключом.
- Склад один, характеристик и серий нет.
- Формы объектов — автоматически сгенерированные платформой.
- В файловом варианте регламентные задания выполняются, только пока открыт клиентский сеанс; для работы по расписанию нужен сервер 1С (или внешний планировщик, вызывающий `POST /exchange/pull-orders`).
