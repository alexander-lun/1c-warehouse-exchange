# Склад: обмен с маркетплейсом

Демонстрационная конфигурация 1С:Предприятие 8.3 (режим совместимости 8.3.24) — небольшой склад с адресным хранением, который получает заказы с маркетплейса, резервирует под них товар, собирает заказы по ячейкам и отдает остатки обратно. Снаружи доступен REST API для ТСД, WMS и курьерской службы.

**Стек:** 1С:Предприятие 8.3 (управляемые формы, режим совместимости 8.3.24), HTTP-сервисы, REST API, JSON, обмен с маркетплейсом, регламентные задания, СКД, печатные формы (MXL, PDF), адресное хранение (ячейки, размещение, отбор), роли и права, управляемые блокировки, Python (pytest, FastAPI), BSL Language Server, GitHub Actions.

Что внутри:

- **REST API на HTTP-сервисе** — остатки, приемка товара, заказы, смена статуса, ручной запуск обмена. Ключ API в заголовке `X-Api-Key`. Описание — [docs/openapi.yaml](docs/openapi.yaml).
- **Обмен с маркетплейсом** — загрузка заказов (инкрементально, по дате изменения), выгрузка остатков, отправка статусов. Регламентное задание + ручной запуск через API.
- **Контроль остатков при проведении** по «новой методике»: управляемая блокировка через `БлокироватьДляИзменения`, запись движений, затем проверка текущего остатка. Проверка на момент документа здесь не годится: два заказа, проведенные в одну секунду, не видят движений друг друга (покрыто тестом с параллельным проведением).
- **Журнал обмена** — регистр сведений с результатом каждой операции.
- **Адресное хранение** — ячейки с порядком обхода, приемка в зону приемки, размещение по ячейкам (вручную или автоматически), отбор заказа по маршруту, печатная форма «Лист отбора».
- **Отчеты на СКД** — остатки по ячейкам, оборачиваемость товаров; данные оборачиваемости отдаются и в API по той же схеме компоновки.
- **Формы и роли** — формы документов с расчетами на клиенте, заполнением и командами; роли «Кладовщик» и «Менеджер по продажам».
- **Интеграционные тесты** на pytest против опубликованной базы и заглушки маркетплейса.

## Как работает обмен

Маркетплейс отдает заказы, измененные начиная с указанной даты (включительно). Отметка «загружено по» хранится в константе.

- Заказ сопоставляется по идентификатору маркетплейса, поэтому повторная загрузка не создает дублей — уже загруженные заказы без изменений пропускаются.
- Если заказ не удалось провести (не хватает товара), он **сохраняется непроведенным**, а не теряется. При следующей загрузке или смене статуса заказ проводится снова — уже текущей датой: резерв возникает в момент проведения, а не в момент первой попытки.
- Если в заказе неизвестный артикул, заказ не создается. Отметка «загружено по» не сдвигается дальше первого заказа с ошибкой, чтобы он попал в следующую загрузку.
- Отмена заказа (с маркетплейса или через API) перепроводит документ без движений — резерв снимается.
- Ошибка отправки статуса на маркетплейс не откатывает смену статуса в 1С: заказ попадает в очередь (регистр `ОчередьОтправкиСтатусов`), и статус отправляется повторно регламентным заданием или `POST /exchange/push-statuses`. Если маркетплейс сам прислал новый статус заказа, запись очереди снимается.
- Параллельные загрузки не создают дублей: заказ, который успела создать соседняя загрузка, считается пропущенным.

## Адресное хранение

```
Поступление ──► ПРИЕМКА ──Размещение──► ячейки хранения ──Отбор по заказу──► отгрузка
                 (зона)    авто/ручное     A-01-01, A-01-02 …   по порядку обхода
```

- **Поступление** кладет товар в предопределенную ячейку «ПРИЕМКА». Регистр `ОстаткиТоваров` показывает свободный остаток (с учетом резервов заказов), регистр `ТоварыВЯчейках` — где товар физически лежит.
- **Размещение** переносит товар между ячейками. Команда «Заполнить из зоны приемки» (и `POST /placements` без тела) подбирает ячейку: товар кладется туда, где он уже хранится, новый — в первую свободную ячейку по порядку обхода.
- **Отбор товаров** вводится на основании заказа в статусе «Ожидает сборки». Количество распределяется по ячейкам хранения в порядке обхода: сначала опустошаются ячейки, которые сборщик проходит раньше, строки сортируются по маршруту. Зона приемки при отборе не используется — неразмещенный товар собирать нельзя.
- **Контроль** — во всех документах по ячейкам: запись движений с `БлокироватьДляИзменения`, затем проверка, что в затронутых ячейках нет минуса. Отбор проверяет, что отобрано ровно то, что заказано. Заказ отбирается один раз: при проведении отбора заказ блокируется (управляемая блокировка), поэтому два сборщика не проведут два отбора одновременно — покрыто тестом.
- **Лист отбора** — печатная форма из макета (ячейка, артикул, товар, количество, графа для отметки). Команда печати есть в форме и списке документа; в API — `GET /orders/{id}/pick-list` отдает PDF.

## Интерфейс

- **Заказ маркетплейса** — форма списка с условным оформлением (ждущие сборки, отмененные, непроведенные из-за нехватки) и быстрым отбором по статусу; форма документа с пересчетом суммы строки и итога на клиенте, составом заказа только для просмотра (его задает покупатель) и командой «Отправить статус на маркетплейс».
- **Размещение товаров** — команда «Заполнить из зоны приемки» с подтверждением перезаполнения.
- **Отбор товаров** — заполнение по заказу при выборе заказа и по команде, печать листа отбора.
- **Отчеты** «Остатки по ячейкам» (группировка по ячейкам в порядке обхода) и «Оборачиваемость товаров» (продано, средний остаток, оборачиваемость в днях, на сколько дней хватит остатка; итоговые показатели считаются выражениями ресурсов СКД, а не суммой строк).

## Роли

| Роль | Доступ |
|---|---|
| `ПолныеПрава` | все |
| `Кладовщик` | поступление, размещение, отбор, ячейки; заказы и номенклатура — только просмотр; отчет «Остатки по ячейкам» |
| `Менеджер` | заказы и номенклатура; складские документы — просмотр; оба отчета, журнал обмена |

Токен маркетплейса менеджеру недоступен: отправка статуса из формы выполняется в привилегированном режиме. Проведение документов — тоже привилегированное, поэтому прав на изменение регистров у ролей нет.

## Метаданные

| Объект | Назначение |
|---|---|
| Справочник `Номенклатура` | товары, артикул индексирован |

| Документ `ПоступлениеТоваров` | приход на склад, в зону приемки |
| Документ `ЗаказМаркетплейса` | заказ: идентификатор, статус, товары; расход с контролем остатков; формы документа и списка |

| Документ `ОтборТоваров` | сборка заказа по ячейкам; ввод на основании заказа; макет и команда «Лист отбора» |

| Отчеты `ОстаткиПоЯчейкам`, `ОборачиваемостьТоваров` | СКД |
| Роли `ПолныеПрава`, `Кладовщик`, `Менеджер` | |

| Регистр сведений `ОчередьОтправкиСтатусов` | статусы, которые не удалось отправить: число попыток, последняя ошибка |
| Перечисления `СтатусыЗаказов`, `НаправленияОбмена` | |
| Константы | адрес и токен маркетплейса, ключ API, отметка загрузки |

Исходники в `src/` — выгрузка конфигурации в файлы (формат конфигуратора).

## Запуск

Нужны платформа 8.3.24 или новее (собирается и проверяется на 8.5.1.1522, Linux; исходники выгружены этой версией), Apache 2.4 и Python 3.11+.

```bash
# база из исходников (+ проверка модулей)
scripts/build.sh build/ib

# ключ API и адрес маркетплейса
scripts/configure.sh build/ib http://127.0.0.1:8090 dev-token my-api-key

# публикация на локальном Apache от текущего пользователя
scripts/publish.sh build/ib warehouse 8081

curl -H 'X-Api-Key: my-api-key' http://127.0.0.1:8081/warehouse/hs/api/stock
```

Для публикации на «обычном» Apache достаточно описать точку публикации в `default.vrd` с `<httpServices publishByDefault="true"/>` и подключить к ней обработчик `1c-application` модуля `wsap24.so` — пример в [scripts/publish.sh](scripts/publish.sh).

Настройки можно задать и вручную: раздел «Склад» → константы.

## Тесты

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
API_KEY=my-api-key PYTHON=.venv/bin/python scripts/test.sh -v
```

`scripts/test.sh` поднимает заглушку маркетплейса ([mock/marketplace.py](mock/marketplace.py)) на порту 8090 и запускает тесты из `tests/`. База между запусками не очищается — тесты используют уникальные артикулы, номера заказов и адреса ячеек.

- `test_api.py`, `test_exchange.py` — API, обмен, резервирование, параллельные загрузки и проведение;
- `test_warehouse.py` — ячейки, размещение (ручное и автоматическое), отбор по маршруту, повторный и параллельный отбор, лист отбора в PDF (текст проверяется через pdfplumber), оборачиваемость.

CI (GitHub Actions) на каждый push: анализ кода 1С BSL Language Server (сборка падает при любом замечании), ruff для Python. Интеграционные тесты требуют платформу и запускаются локально.

Статический анализ — [BSL Language Server](https://github.com/1c-syntax/bsl-language-server), настройки в `.bsl-language-server.json`:

```bash
java -jar bsl-language-server.jar --analyze --srcDir src --configuration .bsl-language-server.json --reporter console
```

## Ограничения

- Пользователи в базе не созданы — она работает без авторизации, API закрыт только ключом. Для работы с пользователями им назначаются роли; пользователю веб-публикации API нужна роль `ПолныеПрава`.
- Склад один, характеристик и серий нет. Вместимость ячеек не учитывается.
- Средний остаток в оборачиваемости — среднее остатков на начало и конец периода, а не по дням.
- Отмена заказа после отбора не возвращает товар в ячейки — это делается документом размещения.
- Формы справочников и регистров — автоматические; формы документов заказа, размещения и отбора — свои. Автотестов интерфейса нет.
- В файловом варианте регламентные задания выполняются, только пока открыт клиентский сеанс; для работы по расписанию нужен сервер 1С (или внешний планировщик, вызывающий `POST /exchange/pull-orders`).
